## New test-only boundary

1. `RuntimePinnedHttpBearerGate` extends the actual Jakarta/Spring servlet `OncePerRequestFilter`, but is **deliberately not a registered Spring bean or FilterRegistrationBean**. Its constructor accepts the already independently reviewed pinned RS256 `RuntimePinnedPrincipalVerifier`. It is **only** able to pass `GET /__s0/auth-probe` and denies every other path with 404. The probe is *not present in the application*, and is registered only inside a test-created Tomcat server. Ambiguous path mappings, non-GET methods, duplicate/missing `Authorization` headers, invalid bearer envelopes, signatures, algorithm, pinned key ID, issuer, target audience or expired tokens fail closed. Scope `orchestrator:read` is required in addition to a valid identity. Identity, token, UID and role are not echoed to the client.
2. The isolated JUnit `RuntimePinnedHttpBearerGateLoopbackTest` starts **real embedded Tomcat with a TCP socket bound to 127.0.0.1 and an ephemeral port**. It creates ephemeral 2048-bit RSA public/private test keys and real signed JWTs and sends actual HTTP requests using Java `HttpClient` rather than MockMvc. It tests missing/forged/wrong-key/wrong-key-ID/wrong-issuer/wrong-audience/multi-audience/expired tokens, wrong scope, spoofed owner and forwarding headers, changed URL and verb handling. The synthetic success response is 204 No Content, no ownership/payload access.
3. The real test-server filter order registers the **existing production** `OwnerlessTaskMissionHttpFilter` first, then the synthetic auth gate. Fake task/mission servlets are explicit *trap handlers* that would return 200 and increment a counter if dispatched. Real requests to task, mission, task history and task write paths carrying even a **fully valid RS256 bearer** must still be 404 with original no-store/nosniff headers and **zero protected dispatches**.
4. GitHub Actions workflow runs checkout pinned to the immutable PR head, Spring/Tomcat Java/JWT tests, original HTTP and SSE lockdown regression, source invariants, then Stage45 NO_GO. No database, cloud service, real production listener, secret or paid services are needed.

## Boundary limitations and mandatory future work

- **Not production resource-server registration:** the candidate filter only exists in repository source and test-constructed Tomcat, and the harmless probe servlet exists only inside JUnit. It does not enforce authentication on the *actual running Spring Boot service*, any user-facing path, Gateway proxy, direct-port backend, API service, websocket or SSE. A valid Identity JWT plus an orchestrator scope is **not ownership**, tenant membership, task data permission, approval to run a tool, delegation or mission scope.
- **No TLS/mTLS:** the loopback network test uses local unencrypted TCP for deterministic behavior; it is not a proof of HTTPS, mutually authenticated workload identity, SPIFFE trust, certificate revocation, key rotation or public network security. The Platform [draft #346](https://github.com/teldigi5-wq/aetheris-platform/pull/346) separately prototypes TLS/RS256 on User service, not the full Gateway-to-Runtime chain.
- **No token/session revocation:** the pinned verifier checks signature, issuer, audience, issued-at/expiry, role-scope ceiling and fixed local key. It does not check live account state, session revocation, IdP disablement or actual database ownership. Real Runtime direct-port authentication must enforce these before any task/mission customer data route can be unblocked.
- **No migration:** `spring.jpa.hibernate.ddl-auto=update` remains unresolved, actual `TaskEntity` lacks durable ownership on protected `main`, and prior V1/V2 fixtures, RLS policy, JDBC probes and synthetic principal checks remain draft. Do not copy these test artifacts into Spring/Flyway production paths or grant DB privileges.
- Real production routes must remain closed until independently verified workload identity, server-side user session, real authoritative tenant/project membership and object-owned state transitions, multitenant mission/event/SSE isolation and full negative integration are independently certified. This stage **does not change controllers or register any new filter**.

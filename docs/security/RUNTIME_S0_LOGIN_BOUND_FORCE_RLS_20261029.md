## Critical production limitations

**This is not an adoptable production per-person database-account architecture.** Issuing and rotating a unique PostgreSQL login/password for every customer, keeping all connection-pool identities isolated and preventing cross-user connection reuse do not yet have an acceptable scalable model. In production, a shared application DB connection identity **cannot** simply reuse this `session_user` policy to provide per-request user RLS. Do not substitute `SET app.identity_uid` / JWT-claim GUCs: a caller with SQL execution access can spoof them. If a shared privileged DB role or table owner runs customer queries, RLS may be bypassed; `FORCE RLS` alone never overcomes superuser/`BYPASSRLS` privileges.

The helper uses a narrow `SECURITY DEFINER` privileged operation, which requires more defense-in-depth and independent source inspection in any real release (role ownership, immutable search path, public schema protections, no untrusted functions/triggers, query-plan/row-count timing, lock behavior, revoke snapshot consistency and SQL injection risk). Direct SQL grants remain metadata-only and not full task content access. This synthetic test does NOT prove a live Identity account lifecycle, workload trust, real HTTPS direct-port authentication, a scalable connection broker, real JPA migration, production rollback, session/JWT revocation, concurrent revoke/write ordering for all code paths, secure executor, mission data or SSE isolation. A database-authenticated synthetic role and signed UID are only useful after a separate auditable provisioning and lifecycle mechanism is approved.

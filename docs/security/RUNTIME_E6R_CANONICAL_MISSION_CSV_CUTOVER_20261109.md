## Concrete new code

- `orchestrator-service/src/test/resources/security/e6r_canonical_mission_cutover_pg16.sql` adds a **disposable review schema** `e6r_review`. It contains a per-Mission cutover decision with states `QUARANTINED`, `CANONICAL`, `FROZEN`, and a separate transactional request-ID audit. This is NOT a production migration and cannot run on application startup.
- The only decision entrypoint, `e6r_review.operator_decide(mission_id,request_id,want_canonical)`, is a `SECURITY DEFINER` function callable only by a new independent **non-superuser operator-only PostgreSQL role**. Its Mission `FOR UPDATE` row lock serializes the decision with older CSV edits and E6Q `FOR SHARE` link writes. It **never parses or imports historical CSV UUIDs**. An ownerless Mission, nonempty/dirty CSV, terminal Mission, inactive tenant/project membership/workload fence, or a pre-existing mismatched link is quarantined and not promoted. Promotion also requires a complete verified owner UID/tenant/project/fence and empty CSV. Every new decision is paired with an audit record in the same transaction.
- After any Mission has been reviewed, a database trigger rejects **all changes to its legacy `task_ids_csv`** even by the privileged disposable test administrator. Before review, old records are preserved untouched; after quarantine they remain physically present, with no reassigned owner or copied link. A CANONICAL decision cannot be re-promoted or silently overwritten. An authorized operator may change CANONICAL to **FROZEN**; rollback retains links and audit evidence but disables the new canonical reader. FROZEN cannot be re-enabled by an automatic retry, and *does not* grant permission to use CSV again.
- `e6r_review.canonical_task_ids` is a separate **function-only** canonical reader, executable by the already restricted E6P reader login. It returns **only** bounded Task UUIDs (1–25) when the Mission is explicitly CANONICAL **and** the current original Platform RS256 signed session/JTI, signer/epoch, owner UID, tenant, project and active workload membership/fence all match. It locks session, Mission, cutover, membership/fence, link and Task rows through the same data-returning READ COMMITTED transaction. It never reads CSV as authority, never exposes event messages/metadata and has no raw-table SQL grants.
- `RuntimeE6RCanonicalMissionCutover.java` is **unregistered Java** using two independent real SQL login identities, one for operator review and one for signed read. The operator's use of a synthetic request UUID is NOT production approval. The reader accepts only the existing cryptographically verified `RuntimePinnedPrincipalVerifier.VerifiedPrincipal`, requires read scope, uses parameterized JDBC, a writable primary, explicit READ COMMITTED transaction and three-second query timeout. No Spring bean, controller, TaskService/MissionService modification, migration runner, cron, public Task route or SSE has been added.
- Existing Task/Mission API paths remain unconditionally **404** under the original `OwnerlessTaskMissionHttpFilter`.

## Nine real PostgreSQL16 security acceptance cases

The new `RuntimeE6RCanonicalMissionCutoverPg16IT` inherits the original real Platform issuer fixture, with independently persisted developer and read-only consumer identities and separate SQL roles. Each test executes the actual PostgreSQL16 functions:

1. A pre-upgrade **ownerless historical Mission** with an old CSV including multiple Task IDs is explicitly QUARANTINED. No Task link is imported. The original CSV bytes remain, and subsequent CSV mutation is rejected.
2. A newly owned Mission containing an unverified CSV reference is QUARANTINED. A different owned Mission with a malicious cross-owner junction link inserted by the disposable test administrator is also QUARANTINED; no signer-based promotion shortcut is accepted.
3. A valid new signed Task↔Mission link remains invisible through the canonical reader **until** a restricted operator explicitly promotes a valid, empty-CSV, owner-bound Mission. After promotion the canonical function returns only the proper Task ID.
4. Operator SQL LOGIN cannot SELECT raw Mission tables; reader LOGIN cannot call the cutover decision function. An unenrolled but correctly signed JTI, another user's principal, wrong tenant/project and invalid requested limit do not return data.
5. Repeating a decided promotion or using an old request ID does not change the state/audit; post-promotion writes to CSV are rejected even by the disposable test administrator.
6. A separate database transaction performing a pending legacy CSV edit holds the Mission row lock. The operator promotion hits a bounded SQL timeout, **not** a false positive. Once the pending transaction rolls back, explicit promotion can succeed.
7. Operator rollback changes CANONICAL to FROZEN, disables the canonical reader and leaves existing Task links and audit records intact. Re-promotion remains forbidden; old CSV edits remain blocked.
8. An uncommitted membership revocation blocks the canonical reader on the actual authority row lock and yields a bounded SQL failure instead of leaking a stale authorized Task ID. Rolling back the revocation restores test-only access.
9. Revoking the actual Platform-signed JTI through an independent restricted revoker LOGIN makes canonical Task reads return no data, without deleting or rewriting the stored link.

## Critical separation from production authorization

- **CANONICAL is a migration mode, not an independent owner grant.** Every read still requires current registered signed identity, owner/tenant/project/fence and database row locking. The operator role is not a replacement for an independently approved user/workload authorization system.
- The E6R canonical reader is **new and opt-in**. The pre-existing E6Q preview event-header function and link function remain independently callable by their existing restricted review roles. FROZEN disables the **new canonical reader**, **not every historical preview function**, because they are intentionally unregistered and separate. Before a real application cutover, all exposed resource-read, event, mission and agent paths must have a single independently reviewed canonical authorization source and consistent lock/rollback gates.
- A real operator identity, signed approval workflow, immutable external audit log, certificate-backed login, approval quorum, and production change window are **not implemented**. The test-only SQL login and request UUID do not prove real human authorization. A PostgreSQL table owner/superuser could bypass the trigger; privilege separation and physical backup custody must be designed for the real environment.
- No actual production schema history/migrator (Flyway/Liquibase), migration checksums of the real Mission/Task data, real workload-bound tenant identity, production TLS/mTLS to Identity/Runtime/database, restore high-watermark, WAL/PITR rollback, multi-node ordering, current ownerless data mapping, pagination/cursor correctness or staging release attestation has been completed. The legacy `MissionService` and `MissionSessionEntity` are unchanged, so this does **not** make the existing product Mission API functional.

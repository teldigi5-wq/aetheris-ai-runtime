## W5-L: preregistered paired-comparison protocol (offline, no model calls)

The first real, owner-approved W5-J trial rejected all three designs
with the pinned Qwen2.5 0.5B model. W5-K later changed the proposed
architecture to split identity, home and approach JSON into three
responses; only synthetic fixtures have tested W5-K so far.

W5-L now specifies a reproducible **3 held-out briefs × 2 methods**
comparison manifest: compact single-proposal (up to two design
requests including its existing safe retry) against staged
three-proposal (three design requests without a retry). The methods
**do not have equal compute budgets**, so one arm's higher observed
acceptance alone cannot establish a cost-adjusted win. A proper later
experiment must report per-brief acceptance, bounded rejection codes,
observed design calls, reported model tokens and wall-clock time, as
well as independently reviewed quality. Three paired briefs are not
statistically powered for broad claims.

The standalone W5-L tool is a **pure offline manifest and untrusted
observation summarizer**. It accepts only six fixed, structured
observations with no raw model text, secret fields, dynamic URLs or
extra authorization claims. Missing executions are represented as
NOT_RUN with null metrics, never inferred rejects. The manifest's
SHA-256 checksum detects accidental change but is NOT a signature or
proof of model provenance. Even if every submitted observation says
ACCEPTED, the summary explicitly denies real-model attestation,
human aesthetic approval, statistically reliable superiority and
Stage 45 release authority.

This does not start or authorize a second cloud trial. Real CPU
inference, resource cost and each actual result remain unverified on

fresh approval for the exact commit, method budgets, compute provider
and experiment steps; do not reapply the consumed approval label
from run 41447764457.


### W5-L validity correction: fixed protocol and aggregate serial CPU ceiling

A review found two meaningful holes in the offline paired-comparison
calculator. First, the 55-minute budget was applied separately to each
of six observations, so an apparent comparison could contain over five
hours of aggregate serial time. The protocol now fixes serial order and
rejects any aggregate reported duration above 55 minutes. Second, its
SHA-256 checksum could be recomputed after changing the model tag,
inference budget or brief identities. It remains an unkeyed checksum,
not a security signature, and the summarizer now independently enforces
every fixed method, model version, brief identity, request ceiling,
execution order and no-authority field even when a caller rehashes a
tampered protocol.

The offline summary continues to treat all reported measurements as
**unverified**, rejects inconsistent accepted-token and request counts,
and never grants release permission. These controls are prerequisites
for a future approved experiment, not evidence of real inference,
performance, originality or production readiness.


### W5-L source-brief content pin (case-name substitution prevented)

The comparison now pins a canonical SHA-256 digest of the **entire
three-brief JSON payload**, including audience, purpose and every
constraint, not just the three project slugs. Both manifest creation
and receipt summarization require this constant digest. Modifying a
brief while keeping its slug and recomputing the unkeyed manifest
checksum fails closed. This is a fixed scientific input control; the
SHA-256 value itself is not a signature of actual inference or its
origin, and any later legitimate brief edit requires explicit protocol
review and versioning. Resource durations remain self-reported;
aggregate per-case generation time is not a substitute for an
independent full-job wall-clock timeout.


### W5-L v2: design acceptance only, independent of downstream site checks

The first W5-L comparison protocol could count CSS generation,
compilation, or Chromium failure codes as failures of the design
generation method. That confounded a study comparing compact and
three-stage JSON design generation with later shared website gates.

The protocol is now V2, with scope DESIGN_VALIDATION_ONLY. A
reported ACCEPTED design means only that the complete two-page
JSON proposal passed the existing W5-A design validator. It does
not indicate that model-authored CSS, compilation, browser testing,
accessibility, visual quality, or release approval passed. CSS,
compiler and browser failure codes are not valid DESIGN rejections.
A reported schema, completion or response-budget rejection requires
at least one design request. Only model unavailability or transport
failure can explain a zero-call rejected design observation.
All observations remain SELF-REPORTED and UNVERIFIED.

The semantic change uses new V2 protocol and summary kinds so old
V1 manifests are not mixed with design-only V2 observations. The
real CPU workflow, release restrictions, and independent browser
gates remain unchanged. No model inference was authorized or run.

### W5-L V3: independently pinned metadata-receipt verification (offline only)

`w5l_research_receipt.mjs` emits a deterministic SHA-256 receipt that binds
the exact W5-L protocol/brief digest, source commit and six validated

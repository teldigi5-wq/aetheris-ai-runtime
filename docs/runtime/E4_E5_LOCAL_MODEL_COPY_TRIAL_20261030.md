## New executable local pathway

`tools/enterprise/e3_factory/e5_local_copy_trial.py` provides:

1. **Plan-only default:** `python tools/enterprise/e3_factory/e5_local_copy_trial.py --model qwen2.5-coder:1.5b` prints the installed-model-unverified, NO-INFERENCE / NO-GO plan with zero file, model or external network requests.
2. **Deliberate operator-only local trial:** on the owner's *own PC*, create a bounded and unverified **noncustomer** local `target/e5/creative-brief.json` with the exact existing E5 schema. Then, only for a deliberately installed, allowlisted Ollama model, explicitly opt in with `--run-local`, `AETHERIS_E4_EXPLICIT_LOCAL_SESSION_OPT_IN=yes` **AND** `AETHERIS_E36_LOCAL_INFERENCE_OPT_IN=yes`. High-resource models also require `AETHERIS_E38_HIGH_RESOURCE_MODEL_OPT_IN=yes`; that flag is not a promise of GPU compatibility. No model installation/pull or cloud inference is implemented.
3. **Hard one-attempt budget:** instance-level thread lock consumes exactly one request attempt **before** any provider inventory lookup, including on failure, with no retry or fallback. The existing E4 model registry/route policy verifies model allowlisting and installed-model inventory evidence. A claimed model tag is NOT cryptographic model-identity attestation or independent performance certification.
4. **Minimum local prompt disclosure:** only the brief's brand name and small lexical requirement/prohibition sets are sent to the fixed localhost Ollama endpoint, along with exact JSON schema and text-only constraints. The tool does not send website source files, browser histories, credentials, customer documents or secret environment variables to any model. If the brand is sensitive, **do not use this experiment without a separate privacy review**. No network calls happen absent all opt-in flags.
5. **No direct model-to-code or deployment path:** treat the response as untrusted data. Require exact Ollama model+completion envelope, 1,400-byte bounded JSON, duplicate/markup/URL/control rejection via the existing E5 copy parser, independent exact-brand and whole-word brief compliance via E5 #225, then package **only** the already trusted, HUMAN-CODED E3.9H WebGL reference with escaped copy replaced. No model-authored CSS, JS, markup or assets can enter the output.
6. **Review evidence only:** fixed local files `target/e5/local-model-copy-trial-preview.zip`, `local-model-copy-trial-evidence.json` and `local-model-copy-trial-receipt.json`. The receipt records untrusted provider-reported model ID and SHA-256 of provider response plus preview/evidence integrity hashes. It says the provider's identity is not cryptographically attested, the **site code is human-written**, only proposal copy could be model-produced, model authorship is independently unverified, and no deployment or owner approval was issued. This is **not a signed evidence chain**.
7. **Fail-closed:** invalid/unknown/uninstalled/high-resource-without-opt-in models, provider errors, bad envelope, unsafe creative brief or denied independent review produce no new review artifact and do not print untrusted response text or local paths. Existing E5 output ZIPs are separate and not overwritten.

## Follow-up task-scope security correction (30 October 2026)

Independent review identified that the first adapter prototype reused E4's existing `scroll` model route task for a *website-copy* generation request. This was not semantically the same capability, so the draft now adds **`website-copy` as a distinct E4 route-admission task**. The E4 policy explicitly DENIES this task for remote/OpenRouter providers even with zero-price catalog and consent declarations. Existing code-repair paths are restricted to the original `e36.CATEGORIES = {scroll,mobile,reduced}`, including the original code-repair CLI; they cannot invoke the website-copy task accidentally. New E4 negative tests cover the separate local-only admission, cloud denial and code-repair prohibition. E5 uses precisely `TASK = "website-copy"` when doing its own fully opt-in local Ollama copy trial; it does not grant model-written CSS, arbitrary JavaScript, shell execution, customer-data disclosure or any production deployment permission. These restrictions are now required by the exact-head CI.

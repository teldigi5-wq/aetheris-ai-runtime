# E3.2 — Three frozen browser defects and strictly allowlisted text patches

**DRAFT, CI-only, no model-generated fixes, no physical PC access, no owner approval and no production deployment.**

## What works in source

Starting from E3.1 PR #118, a Python multi-fault gate extends the same tested premium CSS 3D laptop website with three deterministic, predeclared defect fixtures:

| Fixture | Single intentional source change | Independent browser detector |
|---|---|---|
| `scroll` | Replace scroll-derived progress with fixed zero in generated `site/main.js` | Chromium reads actual stage progress after scrolling to 82%; expects over 70 |
| `mobile` | Inject an 850px minimum page width into the mobile CSS media rule | Chromium checks document scroll width versus its real 390px viewport |
| `reduced` | Disable JavaScript reduced-motion preference recognition | Chromium launches with `prefers-reduced-motion: reduce` and reads actual stage motion state |

`multi_fault.py` generates a **candidate JSON proposal** from the frozen case, with only one literal replacement, fixed path, exact broken source SHA256, target source SHA256 and expected browser fault code. The proposal is treated as untrusted during repair. Arbitrary diff hunks, inserted JavaScript, unknown case IDs, additional keys, changed paths, symlinked inputs, mismatched hashes and oversized proposals fail closed. Only a proposal identical to the reviewed rule may be applied, only to the generated site's two known files.

A separate Playwright `fault_contract.mjs` checks actual Chromium DOM/browser state, writes observed values and one case-specific failure code. The deterministic repair may proceed only when that report identifies the exact expected failure. After repair, the generated bytes must match the original frozen site hashes and the browser must pass. At the end, original E3.0 independent end-to-end browser QA runs again.

**Accuracy:** These are **three known frozen faults**, not unseen defects. The repair policy knows the exact original bytes and repair in advance. The future agent/model patch facility is NOT implemented, and this benchmark cannot be used as AI repair success-rate evidence. Browser diagnosis files are CI fixtures, not cryptographically authenticated human approvals.

## Security execution boundary

Each build/seed/repair phase is launched using the inherited E3.1 Docker runner with **real inspected** settings: no worker network, one CPU, 256 MiB memory/swap, 64 process limit, read-only root filesystem and repository mount, writable temporary target only, no Linux capabilities, no-new-privileges, nonroot host UID, and fixed 45-second wall-clock timeout. Only the three frozen scenario names can be accepted from the additional command argument.

The Playwright browser QA harness and dependency installation run on disposable CI-host infrastructure, separately from the network-disabled Python worker. The CI/host access policy is **not** a certification of an arbitrary hostile container or untrusted code executor.

The work changes no canonical Aetheris agent identity, tool grant, authenticated owner consent, enterprise mapping, financial/trading permission, real desktop command or production service. Stage45 13-blocker certification remains absent/unexecuted on this stacked branch. The physical Windows owner-PC and production are still **NO_GO**.

## Independent checks

1. Ubuntu and Windows adversarial Python tests: all frozen restorations plus missing or unrelated browser diagnosis, malicious path traversal, injected code, forged base digest, added proposal fields, oversized proposal, modified source, disallowed CLI, repeat seed, and symlink refusal.
2. Disposable Ubuntu Docker + real Chromium: each scenario must **fail before** with the exact correct case-specific code, then **pass after** applying the allowed restoration.
3. Independently verify every repaired file has the original SHA256, real Docker inspect configurations, browser DOM state and final original full-browser regression.
4. Run the complete Java orchestrator regression, plus no-new-authority source checks.
5. Attach actual browser before/after screenshots, diagnoses, repair JSON, site bytes and sandbox inspection reports to GitHub Actions. Any CI failure must remain visible; no synthetic pass counters.
